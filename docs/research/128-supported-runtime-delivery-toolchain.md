# Supported runtime and delivery toolchain

Research for [Research the supported runtime and delivery toolchain](https://github.com/zwergius/el-danes/issues/128), checked 2026-08-08 against the repository default branch at `97ed2bc84eb9de0c382f5d2248ea1bfc6fa5c8e6` and the pending [Cloudflare preview E2E workflow](https://github.com/zwergius/el-danes/pull/121).

## Decision

Standardize the dependency migration on **Node.js 24.19.0 (Krypton LTS) and its bundled npm 11.17.0**. Node 26 is Current, not LTS, while Node 24 is the latest LTS line and is explicitly within Playwright's supported Node versions. The Node distribution index identifies 24.19.0 as the latest Node 24 LTS release and records npm 11.17.0 as its bundled npm version. [Node.js release policy and status](https://nodejs.org/en/about/previous-releases) · [Node.js distribution index](https://nodejs.org/dist/index.json) · [Playwright system requirements](https://playwright.dev/docs/intro#system-requirements)

Use an exact root `.node-version` containing `24.19.0` as the shared runtime pin for local development, GitHub Actions, and Cloudflare Pages. Add `engines.node: "24.x"` and `engines.npm: "11.x"` as the human- and npm-visible support contract, but do not rely on `engines` for deployment: Cloudflare Pages build system v3 explicitly does not detect Node or package-manager versions from `package.json`. Configure `actions/setup-node` with `node-version-file: .node-version`; Cloudflare recognizes `.node-version` and supports Node versions newer than its default. [setup-node version-file support](https://github.com/actions/setup-node/blob/main/docs/advanced-usage.md#node-version-file) · [Cloudflare Pages build image](https://developers.cloudflare.com/pages/configuration/build-image/)

Node is a build-and-test runtime for this project, not a production server runtime. `@sveltejs/adapter-static` prerenders the site into files, and Cloudflare deploys those files. Preserve the existing adapter contract: `pages: 'build'`, `assets: 'build'`, `fallback: '404.html'`, `strict: true`, and the current prerender entries. Current SvelteKit supports Node 24 (`node >=18.13`), current `adapter-static` remains compatible with SvelteKit 2, and Cloudflare documents `build` as the output directory when the static adapter is used. [SvelteKit package runtime and peer requirements](https://github.com/sveltejs/kit/blob/main/packages/kit/package.json) · [adapter-static requirements](https://github.com/sveltejs/kit/blob/main/packages/adapter-static/package.json) · [SvelteKit static adapter options](https://svelte.dev/docs/kit/adapter-static) · [Cloudflare SvelteKit deployment guide](https://developers.cloudflare.com/pages/framework-guides/deploy-a-svelte-kit-site/)

## Required implementation changes

1. Add `.node-version` with the exact value `24.19.0`. Add the Node 24/npm 11 `engines` contract to `package.json`, and align `@types/node` to major 24 so TypeScript cannot accept Node 26-only APIs that are absent from the deployed build runtime.
2. Recreate `package-lock.json` under Node 24.19.0/npm 11.17.0 when the dependency cluster is upgraded, then use `npm ci` for verification and GitHub Actions. The repository's lockfile is already format 3; npm documents format 3 as the npm 9-and-newer format, backwards compatible to npm 7. `npm ci` requires the manifest and lockfile to agree, never rewrites either, and therefore supplies the frozen install needed for CI. [npm lockfile format](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/#lockfileversion) · [npm ci guarantees](https://docs.npmjs.com/cli/v11/commands/npm-ci/)
3. In every Actions job that executes project JavaScript, replace `node-version: 22` with `node-version-file: .node-version`. Keep npm caching keyed by `package-lock.json`; `setup-node` caches npm's global package data, not `node_modules`. [setup-node npm caching](https://github.com/actions/setup-node#caching-global-packages-data)
4. Keep third-party actions pinned to immutable commits. As of the research date, the latest stable official releases and pins used by the pending preview workflow are:

   - [`actions/checkout@v7.0.1`](https://github.com/actions/checkout/releases/tag/v7.0.1) — [`3d3c42e5aac5ba805825da76410c181273ba90b1`](https://github.com/actions/checkout/commit/3d3c42e5aac5ba805825da76410c181273ba90b1)
   - [`actions/setup-node@v7.0.0`](https://github.com/actions/setup-node/releases/tag/v7.0.0) — [`820762786026740c76f36085b0efc47a31fe5020`](https://github.com/actions/setup-node/commit/820762786026740c76f36085b0efc47a31fe5020)
   - [`actions/upload-artifact@v7.0.1`](https://github.com/actions/upload-artifact/releases/tag/v7.0.1) — [`043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`](https://github.com/actions/upload-artifact/commit/043fb46d1a93c77aae656e7c1c64a875d1fc6a0a)

   These action releases run on their own embedded Node 24 runtime; that is separate from the Node version installed for project commands. The Node 24 action generation requires Actions Runner 2.327.1 or newer. GitHub-hosted `ubuntu-latest` satisfies that boundary; any future self-hosted runner must be checked before adoption. Checkout v7's new fork protection applies to trusted `pull_request_target` and `workflow_run` checkouts, not this repository's `pull_request` workflow. [checkout runtime and runner boundary](https://github.com/actions/checkout#checkout-v5) · [checkout v7 behavior](https://github.com/actions/checkout#checkout-v7) · [setup-node action runtime](https://github.com/actions/setup-node/blob/main/action.yml) · [upload-artifact action runtime](https://github.com/actions/upload-artifact/blob/v7.0.1/action.yml)

5. Preserve the Playwright sequence `npm ci`, then `npx playwright install --with-deps "$BROWSER"`, then the named test project. Installing after `npm ci` guarantees that browser binaries match the locked Playwright package; installing one matrix browser at a time preserves the current job isolation. Do not add a browser-binary cache: Playwright explicitly advises against it because restoring the cache costs about as much as downloading and Linux system dependencies are not cacheable. [Playwright CI sequence](https://playwright.dev/docs/ci#introduction) · [Playwright browser installation](https://playwright.dev/docs/browsers#install-system-dependencies) · [Playwright caching guidance](https://playwright.dev/docs/ci#caching-browsers)
6. In Cloudflare Pages, confirm build system **v3**, build command `npm run build`, and output directory `build`. Keep Pages' automatic dependency installation for this migration to avoid coupling a dashboard install-mode change to the runtime upgrade; the committed lockfile still determines the dependency tree. Confirm the project is reading the committed `.node-version`. Cloudflare's v3 default is Node 22.16.0/npm 10.9.2, but it supports any Node version via `.node-version` or `NODE_VERSION`; pinning is therefore required to prevent CI/Pages drift. [Cloudflare build image and override policy](https://developers.cloudflare.com/pages/configuration/build-image/) · [Cloudflare build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/)

## Delivery invariants

- The dependency update must not replace `adapter-static` with a server adapter or change the `build` output contract. A successful build must still contain the prerendered localized routes and `build/404.html`. Because SvelteKit treats any configured `fallback` as satisfying the adapter's strictness check, the existing `fallback: '404.html'` means `strict: true` cannot by itself prove that every intended route was prerendered; verification must compare the generated route inventory explicitly. [SvelteKit static generation and strictness](https://svelte.dev/docs/kit/adapter-static)
- Keep Cloudflare's Git integration and same-repository pull-request preview behavior. Pages does not create previews for fork pull requests. Each deployment receives an immutable hash URL while a branch alias moves to the newest deployment, so preview E2E must continue resolving the deployment associated with the exact pull-request head SHA rather than testing the moving alias. [Cloudflare preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Cloudflare GitHub integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/)
- Keep runtime-affecting pull requests gated by all configured Playwright projects against the immutable Pages preview. Documentation-only and draft handling can remain unchanged.
- Re-resolve action release tags to immutable SHAs immediately before the implementation pull request. The pins above are a dated answer, not an instruction to follow mutable major tags.

## Risks and checks

- **Cloudflare build-image drift:** Pages v3 rolls preinstalled software forward and does not read `package.json` engines. The exact `.node-version` is the control; verify the Pages build log reports Node 24.19.0 and npm 11.17.0. Cloudflare plans to migrate v1 projects to v3 on 2026-09-15 and v2 projects on 2027-02-23, so confirm the project is already on v3 rather than waiting for an automatic migration. [Cloudflare build image policy](https://developers.cloudflare.com/pages/configuration/build-image/#build-image-policy)
- **Lockfile/runtime mismatch:** regenerate the lock only under the selected runtime, run a clean `npm ci`, and fail on manifest/lock disagreement. Do not introduce install flags unless they are committed in project `.npmrc`, because npm requires `npm ci` to use the same tree-shaping flags that created the lock. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/)
- **Native or postinstall changes:** Node 24 and npm 11 can expose dependency lifecycle or native-binary failures. The runtime cluster must pass clean install, `npm run build`, `npm run verify`, and a Cloudflare preview build before merging.
- **Browser compatibility:** every Playwright version is coupled to particular browser builds. Update the package and browsers together; never reuse browser binaries from the previous lockfile. [Updating Playwright](https://playwright.dev/docs/intro#updating-playwright)
- **Behavior regression:** compare route inventory and the generated 404 fallback before and after the cluster, then run the complete preview matrix. Static output means there is no production Node process to smoke-test; the deployment checks are the generated artifact and Cloudflare-served behavior.

## Implementation boundary

This research selects and constrains the runtime/delivery stack. It does not upgrade dependencies, alter workflow or Cloudflare settings, or change application behavior.
